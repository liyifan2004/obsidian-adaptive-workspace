# 0008. onEvaluate 命令按「同一命令最小间隔」限流（leading + trailing）

日期：2026-10-23　状态：已接受（实施同日）　关联：ADR 0004（onEvaluate 为预留触发语义的落地）、CHANGELOG_DEV O-06/O-11

## 背景

`trigger: "onEvaluate"` 的语义是"每次匹配评估都执行"（ADR 0004 预留，已实现）。但评估由环境事件驱动：resize/move 有 300ms 去抖，仍是 ~3 次/秒；离散事件立即评估。高频拖动窗口时，同一命令会以 3Hz 反复执行——对同步类命令是浪费，对副作用命令是危险。

曾考虑用 `EnvironmentState.signature` 做"签名相同跳过评估"式去重（O-011 原方案），**否决**：签名不变的一轮评估仍承担 ADR 0001 的再强制收敛职责（用户手动改动受管插件后，正是这些轮次把状态拉回期望值），跳过会静默削弱核心保证；且 resize 过程中 bounds 变化本就改变签名，去重挡不住主要刷屏场景。

## 决策

1. **限流粒度**：按 commandId 独立限流。同一命令两次由 `onEvaluate` 触发的执行至少间隔 `ON_EVALUATE_MIN_INTERVAL_MS`（2000ms，`config.ts`）。
2. **leading + trailing**：间隔外立即执行（leading）；间隔内到达的触发不丢弃，进队列并在间隔结束时**补跑一次**（trailing，合并期间重复触发），保证"最后一次状态变更必然得到一次执行"（无丢唤醒）。
3. **不限流的路径**：`onEnter` 边沿触发（天然一次性）、手动评估（命令面板 "Evaluate workspace rules now" 及改规则后的立即评估，视为显式用户意图，同时取消已排队的补跑）。
4. **可观测**：被推迟的执行写入 evaluate log warning（"deferred by the onEvaluate rate limit"），补跑单独记一条 log；不静默吞掉。
5. **生命周期**：`StateManager.dispose()` 取消挂起 timer（插件卸载经 `register()` 调用）。

## 理由

- onEvaluate 的用户预期是"持续同步"，不是"事件多快就跑多快"；2s 上限对同步类命令足够及时，对副作用命令把最坏频率从 3Hz 压到 0.5Hz。
- trailing 补跑是正确性关键：只做 leading 限流会在"拖动结束恰好落在间隔内"时丢掉最终状态的执行。
- 按命令独立限流而非全局限流：不同命令互不拖累，行为可预测。

## 后果

- 好：高频事件下命令不再刷屏；最终状态保证执行；手动路径行为不变（永远立即执行）。
- 坏：`onEvaluate` 严格意义上不再是"每次评估都执行"（间隔内合并为一次）——语义变化已在 README/F-015 声明。对"必须逐轮执行"的极少数场景（如有损计数类命令）不适用，此类命令应改用 onEnter 或外部节流。
- 跟进：间隔值暂为常量；若用户需要自控，可升级为按动作配置（优化清单 O-15）。
