# 0002. 显示器判定：remote.screen.getDisplayMatching 主路径 + 手动映射降级

日期：2026-09-29　状态：已接受

## 背景

核心需求是"窗口主要位于内置屏还是外接屏"。不能用显示器数量判断；必须绑定到 Obsidian 窗口实际所在的 Display。窗口可能跨屏，Windows 存在 DPI 缩放差异。Electron `screen` 是主进程模块，渲染进程不能直接拿。

## 决策

主路径（实测依据：本机 Obsidian 1.13.4 的 app.asar 自带 @electron/remote 2.1.3，Electron 28.x）：

```
window.electron.remote          → 主进程模块句柄
  .getCurrentWindow()           → 当前 Obsidian BrowserWindow
  .screen.getDisplayMatching(win.getBounds())  → 主要所在 Display
```

- 跨屏处理：不信任单一 API，自行用 `screen.getAllDisplays()` 计算窗口矩形与各 Display 的**相交面积**，取最大者为 dominant display，同时置 `window.spanning = true`（两块以上显示器相交面积均 > 0 且次大占比 > 10%）。`getDisplayMatching` 结果与自算结果不一致时以自算为准（语义更明确），并记入 Diagnostics。
- 坐标：窗口 bounds 与 Display bounds 均为 DIP 虚拟坐标（Electron 同一坐标空间），多屏不同缩放可直接比较；`scaleFactor` 只作为条件数据，不参与几何计算。
- `Display.internal`：**只当提示，不当依据**（Electron 在 Windows 上该字段不可靠）。判定"内屏/外屏"用三级策略：
  1. 设置里有手动映射（用户指定某 display id 为内屏）→ 用它；
  2. 否则 `display.internal === true` → 内屏；
  3. 否则若 `display.internal` 全为 false（Windows 常见）→ 回退启发式：与主显示器（primary）相同则视为内屏（笔记本场景主屏通常为内屏），并在 UI 标注"启发式判断"。

降级路径（`remote` 拿不到时）：DOM 粗粒度模式——`window.screenX/screenY/outerWidth/outerHeight` + `window.screen.avail*` 估算窗口所在屏与最大化/全屏，拿不到 display id 与 internal。Diagnostics 显示当前能力等级（full / degraded）。

## 理由

- `getDisplayMatching` 是 Electron 官方"矩形→最相交显示器"语义，正对需求；自算相交面积是对跨屏场景的显式兜底。
- 手动映射彻底绕开 `internal` 不可靠问题，且实现成本低。
- 降级模式保证未来 Obsidian 移除 @electron/remote 时插件不失效，只退化。

## 后果

- 好：Windows 多屏、DPI 混合、插拔、跨屏都有明确定义；不依赖猜测。
- 坏：`internal` 启发式在"主屏是外接屏"的台式机场景会误判——所以手动映射是推荐配置，UI 引导用户设置。
- 跟进：实现后在真机（笔记本 + 外接屏）验证 getDisplayMatching 与自算的一致性，结果回填本文档。
