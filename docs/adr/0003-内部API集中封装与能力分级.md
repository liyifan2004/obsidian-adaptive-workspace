# 0003. 内部 API 集中封装于单一访问层，并做能力分级

日期：2026-09-29　状态：已接受

## 背景

MVP 必须依赖三类未公开 API：

1. `app.plugins`（enablePluginAndSave / disablePluginAndSave / enabledPlugins / manifests / plugins）——控制其他插件启停；
2. `app.commands`（executeCommandById / listCommands）——执行与枚举命令；
3. `window.electron.remote`（getCurrentWindow / screen）——窗口与显示器信息。

官方 `obsidian.d.ts` 均未类型化（已核对 obsidian-api 仓库），但社区有成熟先例（Plugin Groups、Plugin Manager、QuickAdd、Advanced URI 等）与逆向类型库 obsidian-typings。

## 决策

- 所有内部 API 访问收口到 `src/core/internal-api.ts` 一个文件：运行时特性探测 + 安全包装 + 统一错误处理，其余代码只 import 它的公开接口。
- 类型用 devDependency `@obsidian-typings/obsidian-public-latest`（版本对齐 minAppVersion），不在业务代码里散写 `as any`。
- 运行时输出能力等级：`full`（remote + plugins + commands 全可用）/ `degraded`（缺 remote，DOM 降级）/ `limited`（缺 plugins 或 commands，对应功能禁用并告警）。Diagnostics 实时显示。

## 理由

- 未公开 API 随 Obsidian 版本变动的风险无法消除，只能**收敛爆炸半径**：变动时只改一个文件。
- 特性探测让"API 消失"变成显式降级而不是崩溃（可靠性要求：单点失败不得拖垮插件）。

## 后果

- 好：升级兼容工作量集中；E2E/实机验证点明确。
- 坏：internal-api.ts 需要为每类 API 写探测与 fallback 分支，初期略重。
- 跟进：每次 Obsidian 大版本更新后跑一次 Diagnostics 自检（能力等级 + 三类 API 探测结果）。
